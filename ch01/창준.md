# Chapter 01 - 창준

## 핵심 내용

- 아코디언 하나를 두고 구현 스펙트럼이 넓다: React state 조건부 렌더링(#1) → CSS hidden/show(#2) → 애니메이션(#3) → 바닐라 JS(#4) → **JS 없는 순수 HTML**(#5-1 radio, #5-2 details) → 검색 대응(#6) → 다중 활성화(#7~9)
- 조건부 렌더링(#1)은 닫힌 패널이 DOM에 없어서 Ctrl+F 검색·SEO에 불리하다. CSS hidden 방식(#2)은 DOM을 유지하지만 일반 `hidden`/`display: none`이면 여전히 페이지 내 검색에 안 걸린다.
- `hidden="until-found"`(#6)는 이 문제의 플랫폼 차원 해답: 화면에는 숨기되 **페이지 내 검색과 앵커 이동에는 노출**시킨다. 브라우저가 내부적으로 `content-visibility: hidden`으로 구현하므로 일반 hidden과 달리 레이아웃 박스가 생성된다. 사용자가 검색으로 찾으면 브라우저가 `hidden`을 제거하며 **`beforematch` 이벤트**를 발생시키고, 여기에 토글 핸들러를 걸면 "검색하면 아코디언이 열리는" UX가 완성된다.
- 단, React는 `hidden`을 boolean 속성으로 강제 변환해서 `"until-found"` 문자열이 `hidden=""`으로 뭉개진다 ([React #24740](https://github.com/facebook/react/issues/24740), React 19.2.8에서 `renderToStaticMarkup` 실험으로 직접 확인). 우회책은 대문자 `HIDDEN` 속성 — React의 known props 매칭이 대소문자를 구분해서 "모르는 속성"으로 통과되고, HTML 속성명은 대소문자 무시라 브라우저는 `hidden="until-found"`로 읽는다. 대가는 dev 콘솔 경고와 TS 타입 오류(스프레드로 우회).
- radio input(#5-1)은 "같은 name 중 하나만 checked"라는 브라우저 내장 상태 머신을 제공한다. 여기에 label 클릭 위임 + CSS `:checked` 선택자를 조합하면 JS 한 줄 없이 단일 활성화 아코디언이 된다. → 상세 원리는 아래 심화 섹션
- 다중 활성화(#7~9)는 상태 설계의 문제: 배열/Set으로 열린 id 목록 관리(#7) vs 아이템별 개별 state(#8) vs Context API로 상태 공유(#9). 각각 상태의 소유 위치가 다르다.

## 심화: label–input은 어떤 원리로 연결되는가

#5-1 예제에서 label을 클릭하면 radio가 체크되고 패널이 열린다. JS가 한 줄도 없는데 어떻게 동작할까? 세 개의 층이 쌓여 있다.

### 1층. 연결 — "labeled control" 결정

[WHATWG HTML 스펙](https://html.spec.whatwg.org/multipage/forms.html#the-label-element)은 label마다 딱 하나의 **labeled control**을 정한다:

- `<label for="x">` — 같은 트리에서 `id="x"`인 첫 번째 labelable 요소 (React에선 `htmlFor`)
- `<label><input/>…</label>` — `for`가 없으면 자손 중 첫 번째 labelable 요소가 자동 연결

labelable 요소는 `button`, `input`(hidden 타입 제외), `select`, `textarea`, `meter`, `output`, `progress` 등으로 스펙에 열거되어 있다. 즉 "연결"은 관례가 아니라 **스펙에 정의된 결정 알고리즘**이다.

### 2층. 클릭 위임 — activation behavior

label의 **activation behavior**가 "내가 클릭되면 labeled control을 대신 클릭한다"로 스펙에 정의되어 있다. Chromium 실제 구현은 [`html_label_element.cc`](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/html/forms/html_label_element.cc):

- `Control()` — 1층의 알고리즘대로 연결된 컨트롤을 탐색
- `DefaultEventHandler()` — label에 온 클릭 이벤트를 받아 컨트롤에 **시뮬레이션 클릭을 전달** ("label 클릭 = input 클릭"의 실체)
- `SetActive()` / `SetHovered()` — label의 hover/active 상태를 컨트롤에도 미러링 (label에 마우스만 올려도 컨트롤이 `:hover`가 되는 이유)
- `Focus()` — label로 온 포커스를 컨트롤로 리다이렉트

그래서 label을 탭 버튼처럼 크게 스타일링해도, 어디를 눌러도 브라우저가 알아서 radio를 클릭해준다.

### 3층. 상태 머신 — radio group

같은 `name`을 가진 radio들은 그룹이 되고, 브라우저가 **"그룹당 checked는 최대 하나"** 를 보장한다. 하나를 체크하면 이전 것이 자동 해제된다 — 단일 활성화 아코디언에 필요한 상태 전이가 공짜로 생기는 것. Chromium에서는 [`radio_button_group_scope.cc`](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/html/forms/radio_button_group_scope.cc)가 이 그룹 관리를 담당한다.

### 조립: CSS가 상태를 화면에 반영

```css
/* radio는 시각적으로 숨기고 */
input[type='radio'] { /* 숨김 처리 */ }

/* checked 상태를 형제 선택자로 읽어 패널을 연다 */
input[type='radio']:checked ~ .description { display: block; }
```

정리하면: **클릭 입력은 label(2층)이 받고 → 상태는 radio group(3층)이 관리하고 → 화면 반영은 CSS `:checked` 선택자가 담당한다.** React로 치면 이벤트 핸들러·useState·조건부 렌더링을 각각 브라우저 내장 기능으로 치환한 구조다. 덤으로 label 연결은 스크린 리더에 컨트롤의 접근 가능한 이름(accessible name)을 제공하므로 접근성도 함께 얻는다.
