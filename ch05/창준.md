# Chapter 05 - 창준

## 핵심 내용

- **CSS는 자르기는 하는데, 잘렸는지를 알려주지 않는다.** `-webkit-line-clamp: 3`이면 3줄에서 `…`로 잘리지만, "이 텍스트가 넘쳤는가"를 물어볼 셀렉터가 없다. 그래서 '더보기' 버튼을 띄울지 말지를 정하려면 결국 자바스크립트로 줄 수를 세야 한다. 이 장의 예제들은 전부 **그 한 가지를 어떻게 세느냐**로 갈린다.
- 세는 방법은 ch04와 똑같이 나뉜다. `#1`은 canvas로 우리가 계산하고, `#2`·`#3`은 브라우저가 이미 배치해 둔 `scrollHeight`를 읽는다. 그래서 `#1`만 부정확하다 — 나눗셈은 단어 단위 줄바꿈을 재현하지 못해 **항상 적게 센다.**
- 줄 수는 `Math.round(scrollHeight / lineHeight)`로 구한다. `round`가 필요한 이유는 `line-height: 1.67`이 소수 픽셀(16px 기준 26.72px)을 만드는데 `scrollHeight`는 정수만 돌려주기 때문이다. 3줄이 80.16px인데 80으로 읽히니 `80 / 26.72 = 2.994`가 되고, `ceil`이면 3, `floor`면 2로 갈린다.
- `line-height`를 아예 지정하지 않으면 `getComputedStyle`이 `"normal"`을 돌려주고 `parseFloat("normal")`은 `NaN`이라 계산 전체가 무너진다. SCSS 주석의 `// 2, 3번 방식에서는 필수!`가 이 얘기다.
- **`#2`의 레플리카는 ch04와 목적이 다르다.** ch04에서는 레이아웃 스래싱을 피하려는 것이었지만, 여기서는 **이미 3줄로 잘린 원본을 재도 되는가**라는 질문 자체를 없애려는 것이다. `.text-clone`에는 `display: -webkit-box`도 `-webkit-line-clamp`도 없어 항상 전체 높이를 돌려준다.
- 리사이즈마다 다시 재야 한다. 너비가 바뀌면 줄바꿈 위치가 바뀌어 3줄이던 게 5줄이 되기 때문이다. ch03에서 만든 `viewportContext`를 그대로 재사용했다.

## 심화 1: 왜 `scrollHeight`가 잘린 뒤에도 전체 높이를 주는가

`-webkit-line-clamp`가 걸린 요소는 이렇게 생겼다.

```
                        ┌─────────────────┐
   clientHeight  ┄┄┄┄┄  │ 첫 번째 줄       │
   (3줄까지 보임)        │ 두 번째 줄       │
                        │ 세 번째 줄 …     │
                        └─────────────────┘
                        ┊ 네 번째 줄       ┊  ← overflow: hidden으로 가려짐
   scrollHeight  ┄┄┄┄┄  ┊ 다섯 번째 줄     ┊     그러나 레이아웃에는 존재
                        └─────────────────┘
```

`overflow: hidden`은 **보이지 않게 할 뿐 스크롤 영역 자체는 유지한다.** 네 번째 줄부터도 배치가 끝난 상태이고, `scrollHeight`는 그 전체를 잰다.

여기서 갈리는 게 `visibility`와 `display`의 차이와 같은 축이다.

```
DOM ─▶ 스타일 계산 ─▶ 레이아웃 ─▶ 페인트 ─▶ 합성
                        (배치)     (그리기)
                          ▲          ▲
                          │          └─ overflow: hidden, visibility: hidden 은 여기서만 빠짐
                          └─ display: none 은 여기서부터 빠짐 → scrollHeight = 0
```

`#2`가 레플리카를 쓰는 것도 이 성질에 기대지 않으려는 선택이다. `.text-clone`은 애초에 클램프가 걸리지 않으므로 "잘린 상태에서 재도 되는가"를 고민할 필요가 없다.

```scss
.text-clone {
  position: absolute;
  height: 0;          // clientHeight를 0으로 눌러 내용 높이만 남김
  visibility: hidden; // 레이아웃에는 참여, 그리기만 생략
  left: 10px;         // 원본과 너비를 정확히 맞춰야 줄바꿈이 같아짐
  right: 10px;
}
```

## 심화 2: `#1`의 canvas가 왜 적게 세는가

```ts
Math.ceil(measureText(curr).width / elem.clientWidth);
```

전체 너비를 상자 너비로 나눈다. **글자를 아무 데나 잘라 빈틈없이 채운다고 가정**하는 계산이다. 하지만 브라우저는 단어 단위로 끊으므로 줄 끝마다 여백이 남는다.

```
폭 100px, 글자당 10px, "aaaaa bbbbb ccccc"

계산   ceil(170 / 100) = 2줄

실제   ┌──────────┐
       │aaaaa     │  "aaaaa bbbbb"는 110px → 안 들어감
       │bbbbb     │  50px 버려짐
       │ccccc     │  50px 버려짐
       └──────────┘  → 3줄
```

단어 길이가 폭의 절반을 살짝 넘을 때 최악이라 거의 2배까지 벌어진다. 이 장의 데이터가 영문 lorem ipsum이라 차이가 잘 드러난다.

그럼에도 canvas가 쓸모 있는 자리는 **넣어보기 전에 예측해야 할 때**다. `scrollHeight`는 텍스트를 이미 DOM에 넣은 뒤에야 읽을 수 있다.

## 심화 3: 바닐라 버전(`#4`)이 React 버전보다 단순한 이유

React 버전은 상태가 두 개다.

```tsx
const [showClampButton, setClampButton] = useState(false);
const [isClamped, setIsClamped] = useState(false);
```

바닐라 버전은 클로저 변수 하나로 끝난다.

```ts
let isClamped = false;
```

버튼 표시 여부를 상태로 들 필요가 없기 때문이다. React는 "상태 → 렌더 결과"라는 한 방향 흐름이라 조건부 렌더링을 위해 상태가 필요하지만, 바닐라는 `$content.append($btn)` / `$btn.remove()`로 **직접 붙였다 뗀다.**

```ts
if (linesOverflow) $content.append($btn);
else $btn.remove();
```

대신 잃는 것도 있다. 상태와 DOM이 어긋날 수 있고, 다른 코드가 값을 알 방법이 없다. ch06의 비제어/제어 폼과 정확히 같은 트레이드오프다.

## 메모

- 리사이즈하면 사용자가 펼쳐 둔 것이 다시 접힌다. `setIsClamped(linesOverflow)`가 버튼 표시 여부와 접힘 상태를 한 값으로 같이 정하기 때문이다. 전자는 재계산이 맞지만 후자는 사용자 조작을 존중해야 할 수도 있다.
- `1_r`·`2_r`은 `key={i}`, `3_r`은 `key={text}`로 서로 다르다. `3_r`은 `map`의 `i`를 받아놓고 쓰지 않아 린트 경고가 난다.
- `maxLines = Number.MAX_SAFE_INTEGER` 기본값은 타입이 `maxLines: number`(필수)라 도달할 수 없는 죽은 코드다.
- `if (!viewportWidth) return`이 있어 `ViewportContextProvider`로 감싸지 않으면 측정이 한 번도 일어나지 않는다. ch03 `#3`에서 겪은 것과 같은 함정이라 `Example.tsx`에서 `#1`~`#3`을 Provider로 감쌌다.
