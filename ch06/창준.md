# Chapter 06 - 창준

## 핵심 내용

- **폼의 모든 주제는 "값을 누가 소유하는가" 하나로 갈린다.** 비제어는 DOM이, 제어는 React state가 주인이다. 나머지 차이 — 이벤트 위임 가능 여부, 검증 방식, 리렌더 횟수, 커서 문제 — 는 전부 여기서 파생된다.
- 구분 기호 인풋(`#1`)이 어려운 이유는 **하나의 `input.value`에 "사람이 읽는 표시"와 "프로그램이 쓰는 값"을 겹쳐 놓았기** 때문이다. 매 키 입력마다 `Number` ↔ `toLocaleString`을 왕복시키는데, 그 왕복은 무손실이 아니고 대입은 커서 위치를 버린다.
- `input.value = x` 대입은 **내용 통째로 교체**다. 브라우저는 우리가 어디를 바꿨는지 모르니 커서를 어디 둘지도 모르고, 명세대로 끝으로 보낸다. 커서를 되돌리는 건 우리 몫이다.
- 커서 복원은 **끝에서부터의 거리**를 기준으로 삼는다. 구분 기호는 오른쪽부터 채워지므로 커서 왼쪽만 길이가 변하기 때문이다. `newIndex = 포맷 후 길이 - (값 길이 - selectionStart)`.
- `setCustomValidity(message)`는 **빈 문자열로만 해제된다.** 설정과 해제가 짝을 이루지 않으면 조건이 풀려도 계속 무효 상태로 남는다. 이 장에서 가장 자주 밟는 지뢰.
- `invalid` 이벤트는 **버블링되지 않는다.** React도 위임하지 않고 요소에 직접 붙이므로 `<form onInvalid>`로는 자식 입력을 받을 수 없다. `#2-1`이 `<form onInput>` 하나로 끝내는 것과 대비된다.
- `formController`는 **분기를 데이터로 바꾼 것**이다. 브라우저는 "어떤 규칙이 깨졌는지"만 알려주고 메시지는 못 정하므로, `(필드 × 규칙) → 메시지` 2차원 표가 필요하다. → 상세는 아래 심화 섹션

## 심화 1: 제어와 비제어

### 글자 하나 칠 때 벌어지는 일

**비제어**

```
'ㄱ' 입력 → DOM value 변경 → 화면에 보임
                              (React는 아무것도 안 함, 리렌더 0회)
        ⋮
제출 → new FormData($form) → 그제서야 수확
```

**제어**

```
'ㄱ' 입력 → onChange → dispatch → state 변경 → 리렌더
                                                  ↓
                                        value={state.__id} 대입 → 화면에 보임
```

제어 폼에서 **글자가 보이는 건 내가 쳐서가 아니라 state가 바뀌어서**다. 한 바퀴 돌아야 나타난다. 이 한 바퀴가 모든 차이의 근원이다.

### 코드로 대조

| | `2-1` 비제어 | `2-2` 제어 |
| --- | --- | --- |
| 값 읽기 | `new FormData($el.form)` | `formState.__id` |
| 이벤트 | `<form onInput>` **하나** | 입력마다 `onChange` |
| 값 지정 | `defaultValue` (초기값만) | `value` (매 렌더 대입) |
| 제출 | FormData 수확 + 변환 | state 그대로 |
| 검증 | `validity` + `setCustomValidity` | 렌더 중 파생 가능 |
| 타이핑 시 리렌더 | **0회** | 글자마다 1회 |

### 갈라지는 지점

**① 이벤트 위임이 안 된다.** React는 `value`가 있는데 `onChange`가 없으면 경고한다. 렌더 시점에 **프롭만 보고** 판단하므로 폼에 걸어 버블링으로 받아도 경고는 그대로다.

**② 검증을 어디서 하느냐.** 비밀번호 확인이 이 차이를 잘 보여준다.

```ts
// 비제어 — 값을 손에 쥐고 있지 않아 FormData를 다시 만든다
additionalValidator: ($el, formData) => $el.value === formData.get("password")

// 제어 — 두 값이 이미 있으니 렌더 중에 계산
const passwordMismatch = formState.__password !== formState.__password_confirm;
```

**③ 파일은 제어할 수 없다.** 스크립트로 `value`를 넣을 수 있으면 사용자 몰래 임의 파일을 업로드시킬 수 있어 브라우저가 막았다. **제어 폼을 써도 파일만은 비제어**다.

**④ `transformData`가 제어 폼에는 없다.** 비제어는 DOM에 표시용 값(`"1,234,567"`)이 들어 있어 제출 직전에 되돌려야 한다. 제어는 리듀서가 넣을 때 이미 숫자만 남기고 렌더할 때만 꾸미므로 그 단계가 사라진다.

```
비제어   DOM에 표시용 값 저장  →  제출 직전에 되돌림    (transformData)
제어     state에 순수 값 저장   →  렌더할 때만 꾸밈      (변환 불필요)
```

## 심화 2: `formController`는 왜 이렇게 생겼나

### 해결하려는 틈

```
브라우저가 아는 것   "이 입력은 tooShort 규칙을 어겼다"
사용자에게 필요한 것  "아이디는 네 글자 이상 입력해 주세요"
```

브라우저는 어떤 **규칙**이 깨졌는지만 알려준다. 메시지는 기본 문구뿐이고 필드별로 바꿀 수 없다. 그래서 이 대응표를 우리가 갖고 있어야 한다.

| | `valueMissing` | `patternMismatch` | `tooShort` |
| --- | --- | --- | --- |
| `__id` | 아이디를 입력하세요 | 영어·숫자·_만 | 네 글자 이상 |
| `__name` | 이름을 입력하세요 | 한글만 | 두 글자 이상 |
| `__agree` | 약관에 동의해야… | — | — |

빈 칸은 `undefined`다. 자바스크립트는 없는 속성을 꺼내도 에러가 아니라 `undefined`를 주고, 타입 쪽은 `Partial<...>`로 전부 선택적이라고 선언해 둬 컴파일도 통과한다.

### 표가 없으면

```ts
if ($el.name === "__id") {
  if ($el.validity.valueMissing) $el.setCustomValidity("아이디를 입력하세요.");
  else if ($el.validity.patternMismatch) $el.setCustomValidity("아이디는 영어나...");
  else if ($el.validity.tooShort) $el.setCustomValidity("아이디는 네 글자...");
  else $el.setCustomValidity("");
} else if ($el.name === "__name") {
  // 필드 7개 × 규칙 3개 = if문 20여 개
}
```

필드를 하나 추가할 때마다 **함수를 뜯어고쳐야** 한다.

### 표가 있으면

```ts
const inputController = formController[$el.name];              // ① 행 찾기
const invalidKey = validationKeys.find(k => $el.validity[k]);  // ② 열 찾기
const errorText = inputController?.[invalidKey] || "";         // ③ 교차점 꺼내기
```

함수는 영원히 이 세 줄이고, 필드가 늘어도 표만 고치면 된다.

### `validationKeys`가 따로 있는 이유

두 가지 일을 한다. 첫째, `validity`는 객체지 배열이 아니라 순회할 수단이 없다. 둘째, **배열 순서가 곧 우선순위다.** 아이디에 `!!`를 치면 `patternMismatch`와 `tooShort`가 동시에 참인데, 배열에서 앞선 `patternMismatch`가 이긴다.

`valid`와 `customError`가 빠져 있는 것도 의도적이다. 전자는 유효할 때 참이라 항상 걸리고, 후자는 우리가 설정하는 값이라 읽으면 순환한다.

### `additionalValidator`라는 탈출구

HTML 검증 속성은 전부 **자기 값만** 본다. "이 필드는 저 필드와 같아야 한다"를 표현할 방법이 없어 표에 함수 자리를 하나 뚫어 뒀다. **90%는 선언적인 표로, 나머지 10%는 함수로.**

### 다만 이벤트만으로는 구멍이 남는다

```
1. 비밀번호 "abc" 입력
2. 확인란에 "abc" 입력 → 일치 판정 → setCustomValidity("") → 유효
3. 비밀번호를 "xyz"로 수정 → 확인란에는 이벤트가 가지 않음
4. 확인란은 여전히 '유효' → 네이티브 검증도 통과 → 그대로 제출됨
```

`handleInvalid`가 **이벤트가 난 요소 하나만** 보기 때문이다. 그래서 제출 직전에 폼 전체를 훑는 `checkAdditionalValidity`를 따로 뒀다.

```ts
const results = Array.from($form.elements).map($el =>
  checkAdditionalValidity($el as FormElement, formState),
);
if (!results.every(Boolean)) {
  $form.reportValidity();
  return;
}
```

`every()`를 바로 쓰면 안 된다. 이 함수는 판정만 하는 게 아니라 `setCustomValidity`라는 **부수 효과**가 있어서, 단축 평가로 건너뛴 필드는 낡은 상태로 남는다. `map`으로 전부 돌린 뒤 집계해야 한다.

## 심화 3: `#1`의 커서는 왜 튀는가

### 추적 — `1.5`를 치면 `15`가 된다 (개선 전)

| 누른 키 | 박스 안 값 | `Number()` | 대입 결과 |
| --- | --- | --- | --- |
| `1` | `"1"` | 1 | `"1"` |
| `.` | `"1."` | **1** | `"1"` ← 점이 사라짐 |
| `5` | `"15"` | 15 | `"15"` |

`Number`와 `toLocaleString`은 서로의 역함수가 아니다. `"1."`, `"1.0"`, `"1"`이 전부 숫자 `1`로 뭉개지고, 돌아올 땐 `"1"` 하나뿐이라 나머지는 복원할 수 없다.

### 커서가 끝으로 가는 이유

```
아는 것    값이 "1234"에서 "1,234"로 바뀌었다
모르는 것  옛 문자열의 위치 1이 새 문자열의 어디인가
```

커서 위치는 문자열 안의 인덱스인데, 문자열을 통째로 바꾸면 그 인덱스가 뭘 가리키는지 정의되지 않는다. 명세는 애매함을 없애려고 끝으로 보내도록 정했다.

### 보정 공식

```
d        = 값 길이 - selectionStart      (끝에서부터의 거리)
newIndex = 포맷 후 길이 - d
```

구분 기호는 오른쪽부터 채워지므로 **커서 왼쪽만** 길이가 변한다는 성질을 이용한다.

```
"1|,000"에서 9 입력 → "19,000" 커서 2 → d = 4 → newIndex = 6 - 4 = 2 → "19|,000"
```

음수가 나올 수 있는데 `setSelectionRange`의 인자는 `unsigned long`이라 `-3`을 넘기면 `4294967293`으로 변환돼 **커서가 끝으로 날아간다.** `Math.max(0, ...)`로 막아야 한다.

### 쉼표 백스페이스

쉼표를 지워봐야 포맷팅이 다시 되살리므로 아무 일도 일어나지 않는다. `preventDefault`로 막는 대신 **먹잇감을 바꿔치기**한다.

```
"12,|345" → (2를 미리 제거하고 커서 이동) "1,|345"
          → 기본 백스페이스가 쉼표를 삭제 → "1345"
          → handleInput이 "1,345"로 재포맷
```

## 메모

- `onKeyDown`은 글자가 반영되기 **전에** 발화해 항상 한 박자 늦은 값을 읽는다. 붙여넣기·IME는 아예 잡히지 않으므로 포맷팅은 `onInput`에서 해야 한다.
- `errorRef`에 `ref`를 연결하지 않으면 `errorRef.current`가 `null`이라 핸들러가 예외를 던지고 죽는다. 그러면 에러 표시뿐 아니라 **그 아래의 커서 복원까지 함께** 실행되지 않는다. `!`는 타입스크립트용이라 런타임에는 아무 효력이 없다.
- `checkValidity()`는 판정만, `reportValidity()`는 판정 + 브라우저 기본 말풍선까지. 말풍선은 모양을 바꿀 수 없으므로 디자인을 맞추려면 `checkValidity`로 판정만 받고 `validationMessage`를 직접 그려야 한다.
- 제어 컴포넌트의 초기값을 `undefined`로 두면 "비제어 → 제어" 전환 경고가 난다. `defaultFormState`가 전부 `""`인 게 이 이유다.
- `#1`의 구조적 한계는 그대로 남겨 뒀다 — 소수점 입력 불가, 로케일 의존(`toLocaleString()`을 인자 없이 호출), 2^53 초과 정밀도 손실. 문자열만 다듬고 `Number`를 쓰지 않으면 전부 해결되지만, 책이 왕복 변환을 전제로 진행해 원형을 유지했다.
